# コマンドを実行するとき（dev-standards 共通）

目的：コマンドを、それを流せる環境で流す。作業している環境で流せないものは、同じ失敗を繰り返さずに、流せる環境へ渡す。
AI エージェントの種類や、どこで動いているか（クラウド・手元・CI）に関係なく同じ手順にする。

## 1. この環境で流せるか見る

コマンドを流す前に（手順書・plan・依頼に書かれたコマンドも同じ）、次のどれかが要るかを見る。
要るなら「この環境では流せない」とし、理由を1行で書いて §2 に進む。

- その環境に無いもの：手元にしかないファイルやリポジトリ、認証情報（`gh` のログインなど）、Docker・WSL などのツール
- ネットワークの制限で繋がらない相手
- 入れると依存のインストールの決まり（Docker の中で入れる・証跡を残すなど）に反するツール

前もって分からなければ流してみる。失敗したら理由を1行で書き、上のどれかが原因なら（＝環境のせい）同じく §2 に進む。
コードや手順の誤りで落ちたときは環境のせいではない。ここで止めて普通に直す。

試さずに「オーナーに流してもらう」と決めるときも、必ず §2 を通る。

## 2. 別の環境に頼めるか確かめる

この環境で流せないなら、同じコマンドをやり直す前に（試していなければ、オーナーに手順を渡す前に）、オーナーが用意した別の実行環境
（オーナーの手元の機械に繋がったエージェントなど）に作業を頼める仕組みがあるかを**必ず**確かめる。どう確かめるかは、使っているエージェントの道具に従う。
仕組みがあるかを確かめないまま「頼めない」と決めない。確かめた結果（使える・使えない・その理由）は §4 の報告に書く。

- **頼める**：§3 の形で頼む。
- **頼めない**：オーナーに、その仕組みを有効にするか、手元で流すかを聞く。手元で流してもらうときは、そのまま貼って動くコマンドと、
  結果のどこを返してほしいかを渡す。

## 3. 頼み方

依頼には次を書く。受け手は依頼に書かれていないことはしない。

| 項目 | 例 |
|---|---|
| 何を | `gh actions-lock` を実行して、変わったファイルをコミットする |
| どこで | リポジトリ（パスまたは URL）とブランチ |
| どこまで | 触ってよい範囲（作業ツリーの未コミットの変更や他のブランチには触らない、など） |
| 何を返すか | 実行したコマンド、終了コード、出力の要るところ、作ったコミットやタグ |

- 取り返しのつかない操作（main への push、削除、上書き、外部への公開・送信）は、オーナーがその会話で認めたものだけを頼む。
  認められていなければ、先にオーナーに聞く。
- 秘密情報（トークン・パスワードなど）は依頼にも報告にも書かない。

## 4. 報告

オーナーへの報告では、元の環境で試したこと（試さずに流せないと判断したときはその理由）、§2 で別の環境に頼めるか確かめた結果、
別の環境で流したこと・その結果を分けて書く。

## 5. しないこと

- 環境のせいの失敗を、同じ環境で何度もやり直さない。
- §2 を確かめずに、オーナーに「手元で流してください」と手順を渡さない。
- 決まりを破ってツールを入れたり、制限をすり抜けたりして、無理に元の環境で動かさない。
